# 自适应追问与维度切换指南 (Adaptive Interview Guide)

---

## 1. 候选人回答的实时判定

面试官需根据候选人的每轮回答，敏锐捕捉真实掌握深度，避免被背诵的八股套话迷惑：

| 回答状态 | 表现特征 | 面试官动作 |
| :--- | :--- | :--- |
| **通透清晰** | 概念准确，能主动结合底层原理、工程权衡或代码实例展开 | 向上探顶：深入架构边界、并发冲突、失败容灾与替代方案 |
| **对但偏浅** | 仅给出教科书式定义，未触及机制细节与实际场景 | 横向切入：追问“为什么需要这样设计”、“内部如何工作” |
| **模糊/罗列术语** | 堆砌大量高大上名词（如微服务、高可用、状态机），但逻辑链条跳跃 | 聚焦追问：要求针对其中一个具体术语用通俗白话解释其工作链路 |
| **关键错误** | 核心机制理解出现倒置或重大偏差（如把 RRF 当作简单权重相加） | 确认边界：中性追问一层以排除口误，若仍错误则记录卡点并平滑换题 |
| **明显不会** | 坦言不了解或长时间沉默 | 保护节奏：降低一级确认基础；连续两次不会则果断切出该分支 |

## 2. 项目经历逐层深挖（六层探测模型）

深挖真实项目的黄金链路（按当前回答选择合适层次，不机械逐项硬套）：

```mermaid
graph LR
    L1[1. 是什么] --> L2[2. 为什么]
    L2 --> L3[3. 怎么做]
    L3 --> L4[4. 怎么测]
    L4 --> L5[5. 失败场景]
    L5 --> L6[6. 权衡取舍]
```

1. **是什么 (What)**：该模块在整体系统链路中承担的具体职责。
2. **为什么 (Why)**：为什么不选用市面成熟组件或更直观的方案？关键设计动机何在？
3. **怎么做 (How)**：核心数据流如何流转？状态转移或底层数据结构如何定义？
4. **怎么测 (Verify)**：如何证明该设计确实有效？指标如何度量？基线与评测样本是什么？
5. **失败场景 (Failure)**：上游超时、下游服务宕机、脏数据输入或并发冲突时系统如何自愈或降级？
6. **权衡取舍 (Trade-off)**：引入该方案付出了什么代价（内存、延迟、运维复杂度）？

## 3. 经历真实度与工程凭据核查

当候选人声称“主导核心架构”、“解决高并发瓶颈”或“显著提升检索召回率”时，重点追问：
- **个人实际贡献边界**：从设计、编码、测试到部署，具体哪一部分是候选人独立完成的？
- **量化指标的可比性**：基线是什么？在多大规模的数据集/QPS 下测得？测试方法是自动化脚本还是手动估算？
- **遇坑与攻坚实录**：在实现过程中遇到的最棘手的 Bug 是什么？排查路径是怎样的？
- *注：若候选人表达模糊，仅客观记录“本场证据不足”，不主观臆断造假。*

---

## 4. 编码与推演题考核规范

- 仅在岗位需求或需要验证手写实战能力时引入编码环节。
- 一次仅发布一个明确任务，明确给出函数输入、输出预期与时间/空间复杂度要求。
- 候选人答题期间可中性澄清题意，但不提示解法思路。
- 口头逻辑推演与实际代码运行严格区分记录，严禁将未实际运行的代码标记为“通过测试”。
