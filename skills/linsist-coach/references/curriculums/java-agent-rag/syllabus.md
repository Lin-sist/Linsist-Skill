## 一、Flashback 受控 Agent 核心切片 (S01 ~ S10)

### S01：Native Function Calling 协议与反序列化
- **核心设问**：大模型生成的 `tool_calls` 是如何被 Java 后端安全捕获、校验并映射到具体 Service 的？
- **机制剖析**：模型按已声明工具 Schema 返回参数 JSON，后端绑定 DTO 并进行参数与业务鉴权；不能把“模型返回参数”说成“模型返回 Schema”，也不假设项目必然使用反射调度。
- **核验凭证**：定位 `ToolCallDispatcherTest` 或参数解析异常测试用例。
- **面试 60 秒自述**：“我们在 Java 端自研了原生 Function Calling 解析器，规避外部第三方黑盒框架。通过将模型输出的非确定性 JSON 强转为带 Hibernate Validator 校验的 DTO，在进入业务逻辑前完成防非法注入的静态防御。”
- **48h 复测**：若模型返回了不在白名单里的工具名称或缺失必填字段，Java 端该如何抛出异常并通知模型重试？

### S02：确定性状态机 (AgentStageMachine) vs 自主无限跃迁
- **核心设问**：如何用代码约束模型下一步动作，并保证循环有终止边界？
- **机制剖析**：FSM 用有限状态和迁移规则约束动作；INIT/RUNNING/COMPLETED 等只是教学示例，不是 Flashback 的真实枚举。项目需定位 `AgentWitnessTurnPolicy` 的阶段与追问策略，并结合轮数和时间预算验证终止。
- **核验凭证**：定位 `AgentStageMachineTest` 中断言非法跳转必抛异常的代码。
- **面试 60 秒自述**：“开源框架常因让 Agent 自主决策下一轮行为而导致无法收敛或死循环。我们通过确定性状态机收拢了流转权力，将 Agent 的每一次动作框定在状态图中，确保每一次运行路径都具备可复现性与可审计性。”
- **48h 复测**：画出一个最小循环的教学状态图，并说明它与真实项目阶段枚举的区别。

### S03：HITL 提议与确认分离
- **核心设问**：模型生成了工具参数，为什么还不能直接执行？
- **机制剖析**：当前简历中工具以 `PROPOSED` 状态保存，由用户通过独立业务端点确认执行，并检查所有者、状态与幂等；不要套用通用 `WAITING_CONFIRMATION` 挂起恢复流程冒充项目实现。
- **核验凭证**：定位真实提议持久化、确认入口与重复/越权确认测试，不假定测试类名。
- **面试表达练习**：解释“模型提议权”与“用户确认后业务执行权”的边界；必须有真实项目凭证才用第一人称项目自述。
- **48h 复测**：重复确认或跨用户确认时应如何拒绝？

### S04：确定性护栏与边界
- **核心设问**：为什么对回复和工具参数的校验不能只依赖提示词？
- **机制剖析**：结合业务限制、类型校验、字符 n-gram 覆盖率和最长未覆盖片段检查；高覆盖率不代表语义真实，正则也不能保证拦截所有 Prompt 注入。
- **核验凭证**：定位实际规则和失败分级测试，区分输入、回复与工具参数的检查位置。
- **面试表达练习**：说清一个规则拦截的风险与无法覆盖的反例，不宣称零成本或完全安全。
- **48h 复测**：为什么需要同时考虑覆盖率与最长未覆盖片段？

### S05：全局共享超时预算
- **核心设问**：为什么单次模型超时不等于整个 Agent 请求的超时预算？
- **机制剖析**：简历的前端 30s、后端 24s、单次模型 20s 是该版本配置口径；每次操作前检查剩余预算。跨步骤使用可注入的单调时钟测量耗时，避免墙上时钟跳变。平均耗时不能证明重试必然超时。
- **核验凭证**：定位 `AgentCallBudget` 和相应预算测试；真实默认值以当前配置为准。
- **面试表达练习**：解释后端保留返回业务错误的余量以及“不做隐式自动重试”的取舍。
- **48h 复测**：总预算只剩 500ms，是否启动预计 2s 的调用？

### S06：封闭策略下的单次受控反思
- **核心设问**：什么错误值得再调用一次模型，什么错误应该直接失败或降级？
- **机制剖析**：`AgentReflectionPolicy` 对允许的 typed violation 返回固定纠偏指令；简历介绍时间归属缺失，当前代码还覆盖特定问题数违规。CLOSING 等非获准场景不开环，重写硬上限 1 次、关闭工具；不是任意工具校验失败就反思。
- **核验凭证**：定位 `instructionFor`、重写预算及禁止开环场景测试。
- **面试表达练习**：讲清触发、禁止、上限、再次失败后的降级四个边界。
- **48h 复测**：为什么重写时关闭工具，第二次仍失败时不继续循环？

### S07：MySQL 元数据记忆与分档时间预算
- **核心设问**：没有向量库，如何检索可解释的旧记忆并避免把过去当现在？
- **机制剖析**：`MySqlMemoryPort` 从标签及说明性元数据取片段，不取正文；时间策略打标签并按档位裁剪字符预算。简历的半年以上减半是分档规则，不是指数衰减公式，也不等于自动摘要。
- **核验凭证**：定位 `MySqlMemoryPort`、`AgentTemporalPolicy` 与对应配置、测试。
- **面试表达练习**：区分检索、时间标签、注入预算三个机制；指数衰减仅作为通用可选方案比较。
- **48h 复测**：时间未知或很旧的记忆注入时应如何防止时间归属误导？

### S08：工具安全白名单与入参 Schema 校验
- **核心设问**：大模型生成工具入参时，可能发生参数溢出、脏类型或路径穿越，Java 端如何防护？
- **机制剖析**：工具必须在 Spring 启动时通过注解注册到白名单容器中。入参绑定前通过 JSON Schema 严格校验字段长度、正则表达式与枚举值范围。
- **核验凭证**：定位 `ToolSchemaValidatorTest`。
- **面试 60 秒自述**：“所有向大模型暴露的工具均需在 Java 端进行显式白名单注册。任何未注册工具调用或畸形入参，均会在序列化阶段被直接抛出，无法触碰核心业务逻辑。”
- **48h 复测**：为什么工具入参校验不能只放在 Controller 层，而必须内置在 Agent Runtime 内部？

### S09：轨迹元数据与 OpenTelemetry 对照
- **核心设问**：如何定位一次请求的耗时，同时避免记录用户原文？
- **机制剖析**：先区分结构化轨迹和 OTel Span；所给简历将 OTel 放在 RAG 链路，不能自动搬到 Flashback。通用练习可用 trace_id 关联步骤、时长和结果分类，日志仅记录获准元数据。
- **核验凭证**：分别定位两项目的真实 trace 入口；没有 OTel 依赖或埋点证据就标注为待核验/通用对比。
- **面试表达练习**：解释 traceId/Span 的作用及敏感数据最小化。
- **48h 复测**：不保存 Prompt 原文，如何定位模型阶段的耗时？

### S10：离线 Agent 快照与评测
- **核心设问**：离线行为回归能证明什么，不能证明什么？
- **机制剖析**：使用合成轨迹与快照验证状态、工具权限、预算等不变量；checksum 与变更原因帮助守护基线。离线命令可运行不等于 CI 门禁已配置，也不能证明真实模型质量。
- **核验凭证**：定位真实用例、基线与运行报告，不把示例样本量写成当前统计值。
- **面试表达练习**：说明断言、指标分母、基线变更流程与真实 provider 验证的区别。
- **48h 复测**：为什么不能把自动覆写快照等同于修复回归？

## 二、Enterprise RAG 检索工程核心切片 (S11 ~ S20)

### S11：文档分块策略 (Chunking) 与 Token Overlap 权衡
- **核心设问**：文本切片切得过大或过小分别会带来什么致命问题？Overlap 如何设定？
- **机制剖析**：切片过大导致上下文噪音稀释语义（Embedding 不准）；切片过小导致句子语义碎片化。通常选择 300~500 Tokens 并保留 10%~15% 的 Overlap 以维持上下文连贯性。
- **核验凭证**：定位 `DocumentChunkerTest`。
- **面试 60 秒自述**：“分块质量直接决定了 RAG 效果的天花板。我们根据领域文档的层级结构实现了递归分块与重叠缓冲机制，在保证语义完整度的同时严格控制噪音上下文。”
- **48h 复测**：如果处理的是 Markdown 格式的带表格文档，传统固定长度切片会有什么灾难性后果？

### S12：Milvus 索引与标量过滤
- **核心设问**：IVF_FLAT 的 nlist/nprobe 如何影响召回和查询成本？
- **机制剖析**：当前简历索引口径为 IVF_FLAT + tenant_id/知识库标量过滤；部署事实仍需配置核验。HNSW 的 M/efConstruction/efSearch 作为可选比较，不冒充当前项目默认索引。
- **核验凭证**：定位向量索引创建、查询参数与租户过滤条件。
- **面试表达练习**：区分已用索引、实验比较和未落地方案，不泛称某种索引最优。
- **48h 复测**：过滤条件在相似度检索之后才补做，有什么风险？

### S13：BM25 稀疏检索原理与中文分词定制
- **核心设问**：语义向量检索在遇到型号代码、专有名词时频繁漏召回，BM25 是如何解决的？
- **机制剖析**：BM25 基于词频 (TF)、逆文档频率 (IDF) 以及文档长度归一化公式，对高频专有词有极强的精确命中能力。需配合专业领域词典进行中文分词。
- **核验凭证**：定位 `Bm25SearchEngineTest`。
- **面试 60 秒自述**：“单纯的向量检索存在‘对精确词不敏感’的硬伤。我们引入定制分词的 BM25 稀疏检索作为第一路召回，形成与稠密语义向量互补的黄金组合。”
- **48h 复测**：BM25 公式中参数 $k_1$ 和 $b$ 分别起什么调控作用？

### S14：倒数排名融合算法 (RRF) 数学机制与参数选择
- **核心设问**：两路检索（向量余弦距离 vs BM25 词频得分）的分数维度完全不同，相比经过校准的分数融合，RRF 有什么适用条件与代价？
- **机制剖析**：不同模型的原始分值分布倾斜严重。RRF 通过排名位置计算：$\sum \frac{1}{k + rank}$，无视原始分绝对值。常数 $k$（如 60）用于平滑头部排名的权重差距。
- **核验凭证**：定位 `ReciprocalRankFusionTest`。
- **面试 60 秒自述**：“不同召回算法的分数体系无法等价对齐。我们选用 RRF 算法直接基于排名名次进行多路融合，彻底避开了人工调参归一化的脆弱性与不稳定性。”
- **48h 复测**：如果在 RRF 中两路结果完全无交集，融合后的排名逻辑是怎样的？

### S15：启发式与可选模型重排
- **核心设问**：模型重排有质量收益，为什么仍可能不适合作为默认？
- **机制剖析**：当前简历为启发式默认、NVIDIA 模型可插拔；Cross-Encoder 与 Bi-Encoder 可作原理比较，不预设任意模型或请求规模的收益。比较应固定样本并同时记录质量、延迟与错误。
- **核验凭证**：定位 `HeuristicReranker`、模型实现、registry 与相应 A/B 报告。
- **面试表达练习**：按明确样本和分母说明收益与代价，不能把专项结果当全量基线。
- **48h 复测**：质量提升但 P95 增大时，如何决定默认策略？

### S16：重排故障降级
- **核心设问**：可选模型重排不可用时，返回什么并如何标注？
- **机制剖析**：当前 registry 失败时回退启发式，和“向量库失败后纯关键词检索”是不同的降级层。不要默认描述成纯 RRF 截断，也不承诺未经压测的 200ms SLA。
- **核验凭证**：定位 `RerankerRegistry` 的选择、异常回退与元数据测试。
- **面试表达练习**：讲清降级条件、替代策略、可观察标记和质量代价。
- **48h 复测**：为什么不应把降级返回包装成完整模型重排成功？

### S17：引用片段校验与语义边界
- **核心设问**：引用能够回连原文，能否证明整句回答被原文蕴含？
- **机制剖析**：`CitationValidator` 先匹配身份及 exact 原文，再以交集 token 数 / 引用片段 token 数计算非对称覆盖度，阈值 0.58；拒答清空引用。这不是 NLI，也不是交集 / 并集的 Jaccard。
- **核验凭证**：定位 `CitationValidator.matchSnippet` 的分母与测试；不要只凭变量 overlap 的名字推断公式。
- **面试表达练习**：区分片段来源正确、引用覆盖、语义支持和最终事实正确，NLI 仅作为未落地拓展比较。
- **48h 复测**：为什么词汇重合度高仍可能存在否定、主体或时间误导？

### S18：可靠索引任务账本与分布式租约看门狗 (Lease Guard)
- **核心设问**：超大型文档入库索引耗时数小时，中途节点宕机如何保证任务既不丢失也不重复处理？
- **机制剖析**：在数据库中建立索引任务账本（Task Ledger），状态分为 `PENDING`, `RUNNING`, `SUCCESS`, `FAILED`。Worker 节点定期续租分布式租约（Lease）；心跳超时则状态回退并允许其他空闲节点抢占执行。
- **核验凭证**：定位 `LeaseGuardDistributedTest`。
- **面试 60 秒自述**：“面对长时间离线索引任务，我们设计了带心跳看门狗的租约机制。通过任务状态机与续租机制，彻底解决了 Worker 宕机导致的索引任务死锁与脑裂重复消费。”
- **48h 复测**：数据库行级排他锁与分布式 Redis 租约在长任务调度中各有什么优缺点？

### S19：可信租户过滤与权限
- **核心设问**：如何防止来自请求参数的 tenant_id 覆盖可信登录身份？
- **机制剖析**：当前简历描述将可信登录租户与知识库条件下推到 Milvus 标量查询，并在关系型读写路径检查权限。逻辑过滤不等于物理 partition 隔离，不能混称。
- **核验凭证**：定位身份来源、过滤表达式及读/写/管理权限测试。
- **面试表达练习**：解释全路径约束与越权测试，避免仅凭一处过滤就宣称零越权。
- **48h 复测**：仅在应用内存中后过滤跨租户结果有什么问题？

### S20：RAG 质量门禁与 150 样本评测基准
- **核心设问**：如何科学量化 RAG 检索系统的效果？Recall@K、Precision@K 与 MRR 是如何计算的？
- **机制剖析**：构建 150 个真实问答对（Golden Dataset），自动化度量：
  - **Recall@K (查全率/召回率)**：检索出的前 K 个结果中包含的相关文档数 / 该 Query 真实相关文档总数（即召回比例；在单目标相关文档场景下等价于 Hit@K 命中率）。
  - **Precision@K (查准率/精确率)**：检索出的前 K 个结果中相关文档数 / K（衡量检索结果头部的有效信息密度与噪声控制）。
  - **MRR (Mean Reciprocal Rank)**：所有 Query 首个真实相关文档所在排名的倒数均值：$\text{MRR} = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \frac{1}{\text{rank}_i}$（衡量核心相关结果是否排在首位）。
- **核验凭证**：定位 `RagQualityGateEvalTest`。
- **面试 60 秒自述**：“若在工程中已落地评测体系，可表述：‘我们在项目中建立了端到端的自动化评测流水线。在每次检索调优后，CI 会自动在基准集上跑出 Recall@3、Precision@3 和 MRR 指标，只有综合得分超过门禁阈值才允许合入上线。’（注：若未在实际工程中落地，应遵守经历自述硬约束，转为选型思考陈述：‘在 RAG 质量治理中，行业通用做法是通过 150 样本基准集度量 Recall@K 与 MRR，通过 CI 门禁保证召回调优不劣化。’）”
- **48h 复测**：如果发现 Recall@10 很高但 MRR 很低，通常说明系统的哪个环节需要优化？（提示：说明粗排召回率高，但重排 Reranker 能力不足或位置靠后，未能将核心相关文档排进 Top-3）
