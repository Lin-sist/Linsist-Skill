## 一、Flashback 受控 Agent 核心切片 (S01 ~ S10)

### S01：Native Function Calling 协议与反序列化
- **核心设问**：大模型生成的 `tool_calls` 是如何被 Java 后端安全捕获、校验并映射到具体 Service 的？
- **机制剖析**：模型返回的 JSON Schema 经过反序列化进入强类型 DTO；通过注解驱动的反射调度器匹配对应工具类；执行前验证参数类型、枚举与正则。
- **核验凭证**：定位 `ToolCallDispatcherTest` 或参数解析异常测试用例。
- **面试 60 秒自述**：“我们在 Java 端自研了原生 Function Calling 解析器，规避外部第三方黑盒框架。通过将模型输出的非确定性 JSON 强转为带 Hibernate Validator 校验的 DTO，在进入业务逻辑前完成防非法注入的静态防御。”
- **48h 复测**：若模型返回了不在白名单里的工具名称或缺失必填字段，Java 端该如何抛出异常并通知模型重试？

### S02：确定性状态机 (AgentStageMachine) vs 自主无限跃迁
- **核心设问**：为什么工业级 Agent 必须采用确定性状态机，而不是让 LLM 自行决定“下一步干什么”？
- **机制剖析**：LLM 存在幻觉与死循环缺陷。通过有限状态机（FSM）将 Agent 的生命周期定义为有限集合（INIT -> PLANNING -> TOOL_CALLING -> WAITING_CONFIRMATION -> REFLECTION -> COMPLETED），状态跃迁由代码条件锁定，模型仅在单状态内部进行推理。
- **核验凭证**：定位 `AgentStageMachineTest` 中断言非法跳转必抛异常的代码。
- **面试 60 秒自述**：“开源框架常因让 Agent 自主决策下一轮行为而导致无法收敛或死循环。我们通过确定性状态机收拢了流转权力，将 Agent 的每一次动作框定在状态图中，确保每一次运行路径都具备可复现性与可审计性。”
- **48h 复测**：画出 AgentStageMachine 的 5 个核心状态及转移触发条件。

### S03：Human-in-the-Loop (HITL) 二段式确认机制
- **核心设问**：面对高危写操作（删除数据、调用支付、发送公函），如何保证系统不被模型幻觉误导执行？
- **机制剖析**：当解析出高危工具时，状态机立即挂起为 `WAITING_CONFIRMATION`，向前端返回临时事务 ID 与操作快照。用户在 UI 上点击同意后，凭临时 ID 继续恢复上下文；用户拒绝或超过 TTL 则优雅回滚。
- **核验凭证**：定位 `HitlConfirmationTest` 中模拟用户超时未确认的断言。
- **面试 60 秒自述**：“对于高风险写操作，我们引入了二段式事务确认。模型仅有‘发起申请’的权限，没有‘执行落盘’的权力。通过临时租约令牌和状态机挂起机制，彻底将大模型的非确定性行为隔离在破坏性边界之外。”
- **48h 复测**：挂起等待期间，如果服务重启，如何保证确认凭单的状态一致性？

### S04：确定性防护栏 (Deterministic Guardrails) 机制
- **核心设问**：输入防 Prompt 注入与输出防敏感数据泄露是如何在 Java 端零延迟落地的？
- **机制剖析**：双向流水线拦截器。输入侧使用正则匹配、指令注入模式库与长度限制；输出侧采用敏感词屏蔽、手机号/身份证脱敏过滤器。
- **核验凭证**：定位 `GuardrailsInterceptionTest`。
- **面试 60 秒自述**：“我们在大模型调用前后架设了双向确定性过滤器。在输入阶段拦截越狱指令，在输出阶段对敏感数据执行脱敏，保证企业级数据合规。”
- **48h 复测**：为什么不能只依赖大模型自身的 System Prompt 来防范越狱？

### S05：全局共享超时预算 (Shared Deadline Budget)
- **核心设问**：在一次复杂的 Multi-step Agent 交互中，如何防止单次 LLM 挂起导致整个系统接口超时雪崩？
- **机制剖析**：上游设定总预算（如 30s）。每次底层 HTTP 请求前计算 `Remaining Budget = Deadline - System.currentTimeMillis()`。若剩余预算不足最小阈值直接熔断并进入降级输出。
- **核验凭证**：定位 `DeadlineBudgetInterceptorTest`。
- **面试 60 秒自述**：“为了防止级联超时，我们设计了全局共享超时预算模型。跨多轮 LLM 调用与工具执行共享同一截止时间，让每一次网络 I/O 都能自适应动态调整 timeout，坚决杜绝线程长时间挂死。”
- **48h 复测**：假设总预算剩余 500ms，而模型调用平均耗时 2s，系统应当如何优雅退出？

### S06：单次受控反思 (Single Controlled Reflection)
- **核心设问**：自我反思（Reflection）能提升 Agent 准确率，但如何防止反思引发的死循环和 Token 暴涨？
- **机制剖析**：硬性限制反思计数器 `reflection_count <= 1`。仅在初次工具调用结果校验失败时触发一次定向反思；若二次依然失败则直接标记为不可恢复并向用户求助。
- **核验凭证**：定位 `ControlledReflectionTest`。
- **面试 60 秒自述**：“反思机制是把双刃剑。我们通过强约束将反思次数限制为单次受控，结合明确的重试预算，兼顾了自我纠错收益与成本安全。”
- **48h 复测**：触发反思的核心判定条件（Trigger Condition）应该依据什么来编写？

### S07：MySQL 轻量记忆库与时间指数衰减 (Temporal Decay)
- **核心设问**：不借助复杂的向量数据库，如何让 Agent 高效管理历史会话并兼顾记忆时序？
- **机制剖析**：基于 MySQL 表存储用户会话事件，利用时间衰减公式计算权重：$W = W_0 \times e^{-\lambda \Delta t}$。近期对话拥有高权重，旧对话自动压缩沉淀为摘要。
- **核验凭证**：定位 `TemporalMemoryPolicyTest`。
- **面试 60 秒自述**：“我们采用轻量化 MySQL 承载状态机事件日志，通过指数衰减算法动态加权上下文，既保证了时序事务的严格 ACID，又避免了为简易记忆场景引入维护繁琐的向量库。”
- **48h 复测**：时间指数衰减的公式中，$\lambda$ 参数的大小如何影响记忆的遗忘速度？

### S08：工具安全白名单与入参 Schema 校验
- **核心设问**：大模型生成工具入参时，可能发生参数溢出、脏类型或路径穿越，Java 端如何防护？
- **机制剖析**：工具必须在 Spring 启动时通过注解注册到白名单容器中。入参绑定前通过 JSON Schema 严格校验字段长度、正则表达式与枚举值范围。
- **核验凭证**：定位 `ToolSchemaValidatorTest`。
- **面试 60 秒自述**：“所有向大模型暴露的工具均需在 Java 端进行显式白名单注册。任何未注册工具调用或畸形入参，均会在序列化阶段被直接抛出，无法触碰核心业务逻辑。”
- **48h 复测**：为什么工具入参校验不能只放在 Controller 层，而必须内置在 Agent Runtime 内部？

### S09：分布式链路追踪 (OpenTelemetry Trace)
- **核心设问**：Agent 内部步骤繁杂，线上出现幻觉或高耗时时如何快速定位是哪一步出问题？
- **机制剖析**：每次 Agent 会话生成全局 `TraceId`，各个状态转移、LLM 网络耗时、工具执行时长均作为独立的 `Span` 注入并上报，形成清晰的时间瀑布图。
- **核验凭证**：定位 `AgentTraceInstrumentationTest`。
- **面试 60 秒自述**：“我们将 OpenTelemetry 深度打入 Agent Runtime 内部。每一次状态跃迁、LLM 耗时及工具调用的 I/O 均带有统一 TraceId，使线上每一次决策过程均具备毫米级可解释性。”
- **48h 复测**：在 Span 中记录大模型的 Prompt 时，有哪些安全合规隐患需要注意？

### S10：自动化 Agent 评测套件 (Agent Eval) 设计
- **核心设问**：修改了 Prompt 或状态机逻辑后，如何科学证明 Agent 整体能力提升了而不是劣化了？
- **机制剖析**：基于真实对话日志提炼 50+ 黄金基准用例（Golden Dataset），自动化断言状态转移正确率、工具调用准确率以及任务完成率（Pass Rate）。
- **核验凭证**：定位 `AgentEvaluationRunnerTest`。
- **面试 60 秒自述**：“我们在 CI 流水线中集成了自动化 Eval 套件，杜绝肉眼凭感觉调优 Prompt。每一次代码或提示词提交，都必须通过包含数十个基准用例的回归门禁。”
- **48h 复测**：在 Agent 评测中，针对非确定性的语言生成，常用的断言手段有哪些？

## 二、Enterprise RAG 检索工程核心切片 (S11 ~ S20)

### S11：文档分块策略 (Chunking) 与 Token Overlap 权衡
- **核心设问**：文本切片切得过大或过小分别会带来什么致命问题？Overlap 如何设定？
- **机制剖析**：切片过大导致上下文噪音稀释语义（Embedding 不准）；切片过小导致句子语义碎片化。通常选择 300~500 Tokens 并保留 10%~15% 的 Overlap 以维持上下文连贯性。
- **核验凭证**：定位 `DocumentChunkerTest`。
- **面试 60 秒自述**：“分块质量直接决定了 RAG 效果的天花板。我们根据领域文档的层级结构实现了递归分块与重叠缓冲机制，在保证语义完整度的同时严格控制噪音上下文。”
- **48h 复测**：如果处理的是 Markdown 格式的带表格文档，传统固定长度切片会有什么灾难性后果？

### S12：Milvus 稠密向量检索与索引调优 (HNSW / IVF)
- **核心设问**：面对百万级向量，暴力全量计算不可行，HNSW 图索引的核心参数如何调优？
- **机制剖析**：HNSW 采用多层跳表图结构。构建参数 `M`（每个节点最大连边数）和 `efConstruction`（构建搜索深度），查询参数 `efSearch`。增大 `ef` 能提高 Recall，但增加检索延迟。
- **核验凭证**：定位 `MilvusDenseRetrievalTest`。
- **面试 60 秒自述**：“我们在 Milvus 中选用了 HNSW 索引，在毫秒级召回与召回率之间通过压测标定了最佳的 ef 参数平衡点，支撑高并发语义搜索。”
- **48h 复测**：HNSW 与传统 IVF_FLAT 相比，在内存消耗和检索召回率上有何本质区别？

### S13：BM25 稀疏检索原理与中文分词定制
- **核心设问**：语义向量检索在遇到型号代码、专有名词时频繁漏召回，BM25 是如何解决的？
- **机制剖析**：BM25 基于词频 (TF)、逆文档频率 (IDF) 以及文档长度归一化公式，对高频专有词有极强的精确命中能力。需配合专业领域词典进行中文分词分词。
- **核验凭证**：定位 `Bm25SearchEngineTest`。
- **面试 60 秒自述**：“单纯的向量检索存在‘对精确词不敏感’的硬伤。我们引入定制分词的 BM25 稀疏检索作为第一路召回，形成与稠密语义向量互补的黄金组合。”
- **48h 复测**：BM25 公式中参数 $k_1$ 和 $b$ 分别起什么调控作用？

### S14：倒数排名融合算法 (RRF) 数学机制与参数选择
- **核心设问**：两路检索（向量余弦距离 vs BM25 词频得分）的分数维度完全不同，为什么不能归一化后直接相加？
- **机制剖析**：不同模型的原始分值分布倾斜严重。RRF 通过排名位置计算：$\sum \frac{1}{k + rank}$，无视原始分绝对值。常数 $k$（如 60）用于平滑头部排名的权重差距。
- **核验凭证**：定位 `ReciprocalRankFusionTest`。
- **面试 60 秒自述**：“不同召回算法的分数体系无法等价对齐。我们选用 RRF 算法直接基于排名名次进行多路融合，彻底避开了人工调参归一化的脆弱性与不稳定性。”
- **48h 复测**：如果在 RRF 中两路结果完全无交集，融合后的排名逻辑是怎样的？

### S15：Cross-Encoder 深度重排序 (Reranker) vs Bi-Encoder
- **核心设问**：为什么 Bi-Encoder 向量计算很快却不够准，而 Cross-Encoder 重排能显著提升 Top-3 命中率？
- **机制剖析**：Bi-Encoder 独立计算 Query 和 Doc 的嵌入（无注意力交互）；Cross-Encoder 将 Query 和 Doc 拼在一起送入 Transformer，进行全词注意力交互，评分极精准但推理成本高，因此适合在 Top-30 候选集上做二次精排。
- **核验凭证**：定位 `RerankerServiceTest`。
- **面试 60 秒自述**：“我们构建了两阶段检索管线：初排阶段用双编码器高并发粗筛 Top-50，精排阶段用交叉编码器进行深度注意力重排，以极小延迟代价换取了检索精度的质变提升。”
- **48h 复测**：如果并发流量突增 10 倍，Reranker 服务可能成为瓶颈，如何做资源保护？

### S16：启发式故障降级保护 (Heuristic Fallback)
- **核心设问**：当下游 Reranker 模型服务因显存打满或网络抖动超时，如何保证检索链路不发生 500 崩溃？
- **机制剖析**：在 Reranker 调用外层配置熔断器（Circuit Breaker），设定严格 200ms 超时。一旦触发超时或异常，系统立即退化为“基于 RRF 融合分数截断”，并上报降级打点。
- **核验凭证**：定位 `HeuristicFallbackTest`。
- **面试 60 秒自述**：“在线系统的第一原则是可用性。我们为重排服务设立了硬熔断与启发式降级兜底，确保在模型宕机或显存溢出等极端故障下，用户依然能获得秒级可用检索结果。”
- **48h 复测**：服务降级期间，如何在返回给前端的元数据中优雅标注“结果已经过降级”？

### S17：引用校验门禁 (Citation Validator)
- **核心设问**：如何确保大模型生成的问答不是凭空捏造的幻觉，而是切实源自知识库？
- **机制剖析**：对大模型生成的段落拆解为独立的断言句子（Claims），利用文本匹配和 NLI（自然语言推理）模型验证该 Claim 是否被 Context 中的某一片段强推导支持。无依据句子被直接剔除。
- **核验凭证**：定位 `CitationValidatorTest`。
- **面试 60 秒自述**：“我们在生成结果落盘前增加了 Citation 引用强校验门禁，对回答进行句级别的证据溯源比对，有效阻绝了大模型‘一本正经胡说八道’的企业级风险。”
- **48h 复测**：为什么要求 Citation 的粒度精确到句子而非整个大段落？

### S18：可靠索引任务账本与分布式租约看门狗 (Lease Guard)
- **核心设问**：超大型文档入库索引耗时数小时，中途节点宕机如何保证任务既不丢失也不重复处理？
- **机制剖析**：在数据库中建立索引任务账本（Task Ledger），状态分为 `PENDING`, `RUNNING`, `SUCCESS`, `FAILED`。Worker 节点定期续租分布式租约（Lease）；心跳超时则状态回退并允许其他空闲节点抢占执行。
- **核验凭证**：定位 `LeaseGuardDistributedTest`。
- **面试 60 秒自述**：“面对长时间离线索引任务，我们设计了带心跳看门狗的租约机制。通过任务状态机与续租机制，彻底解决了 Worker 宕机导致的索引任务死锁与脑裂重复消费。”
- **48h 复测**：数据库行级排他锁与分布式 Redis 租约在长任务调度中各有什么优缺点？

### S19：多租户物理/逻辑数据隔离 (Tenant Isolation)
- **核心设问**：企业 RAG 系统服务多个客户时，如何绝对防止 A 公司的机密文档被 B 公司检索到？
- **机制剖析**：在 Milvus 向量集合中通过 `Partition Key` 或独立的 Partition 进行逻辑/物理隔离；在所有 BM25 和 SQL 查询中注入强制强制 `tenant_id` 过滤条件，从底层引擎保证零越权。
- **核验凭证**：定位 `TenantIsolationSecurityTest`。
- **面试 60 秒自述**：“安全合规是企业 RAG 的生死线。我们在存储引擎层引入了基于 Tenant ID 的强隔离约束，无论是向量相似度计算还是关键词召回，跨租户查询在执行计划阶段就会被物理阻断。”
- **48h 复测**：为什么不能只在 Controller 或应用内存层过滤跨租户数据？

### S20：RAG 质量门禁与 150 样本评测基准
- **核心设问**：如何科学量化 RAG 检索系统的效果？Recall@K、Precision@K 与 MRR 是如何计算的？
- **机制剖析**：构建 150 个真实问答对（Golden Dataset），自动化度量：
  - **Recall@K (查全率/召回率)**：检索出的前 K 个结果中包含的相关文档数 / 该 Query 真实相关文档总数（即召回比例；在单目标相关文档场景下等价于 Hit@K 命中率）。
  - **Precision@K (查准率/精确率)**：检索出的前 K 个结果中相关文档数 / K（衡量检索结果头部的有效信息密度与噪声控制）。
  - **MRR (Mean Reciprocal Rank)**：所有 Query 首个真实相关文档所在排名的倒数均值：$\text{MRR} = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \frac{1}{\text{rank}_i}$（衡量核心相关结果是否排在首位）。
- **核验凭证**：定位 `RagQualityGateEvalTest`。
- **面试 60 秒自述**：“若在工程中已落地评测体系，可表述：‘我们在项目中建立了端到端的自动化评测流水线。在每次检索调优后，CI 会自动在基准集上跑出 Recall@3、Precision@3 和 MRR 指标，只有综合得分超过门禁阈值才允许合入上线。’（注：若未在实际工程中落地，应遵守经历自述硬约束，转为选型思考陈述：‘在 RAG 质量治理中，行业通用做法是通过 150 样本基准集度量 Recall@K 与 MRR，通过 CI 门禁保证召回调优不劣化。’）”
- **48h 复测**：如果发现 Recall@10 很高但 MRR 很低，通常说明系统的哪个环节需要优化？（提示：说明粗排召回率高，但重排 Reranker 能力不足或位置靠后，未能将核心相关文档排进 Top-3）
